# Refund idempotency and `paymentRef` uniqueness

**Date:** 2026-08-03
**Scope:** `anonaccred_server` — `refund_manager.dart`, `models/transaction_payment.spy.yaml`, a new model
**Conventions:** `docs/superpowers/DECISIONS.md` — D1 (no compat shims), D3 (batch schema changes, don't dribble a regeneration), D21 (schema needs a decision from the repo owner)
**Depends on:** independent of A2 (`2026-08-02-polar-refund-wiring-design.md`) at the code level — A2 fixes what `PolarRail` produces; this spec fixes what `RefundManager` does with whatever any rail produces. Land in either order, but land A2 first per the agreed sequence.
**Tracked as:** B4 + B5 (`docs/superpowers/TODO-2026-08-02.md`), HIGH #2 + #3 (`docs/superpowers/anonaccred-issues-2026-08-02.md`)
**Schema decision (owner-approved):** `paymentRef` uniqueness is scoped **per rail**, not global — the constraint goes on `(paymentRail, paymentRef)` together, not `paymentRef` alone. Reasoning below.

---

## Two bugs, one root cause: no lookup here is actually unique

`RefundManager.processRefund` (`refund_manager.dart:77-91`) does a plain sequential read → decide → write, no transaction wrapping the whole thing, no lock on anything it reads:

```dart
static Future<void> processRefund(Session session, RefundEvent event) async {
  final context = await _resolveContext(session, event);           // read
  final action = _handler != null
      ? await _handler!(session, event, context)                    // arbitrary dev code
      : RefundAction.revokeAll;
  await _executeAction(session, event, context, action);            // write
}
```

`_resolveContext` (`refund_manager.dart:94-125`) does two lookups that are each individually broken:

1. **`TransactionPayment` by `paymentRef`** (`refund_manager.dart:109-111`) — `findFirstRow` on a column with **no index at all**. `models/transaction_payment.spy.yaml` indexes `internalTransactionId` (unique) and `transactionTimestamp` (non-unique); `paymentRef` — the field this exact lookup filters on — has neither. Two consequences: the lookup is a sequential scan today, and if any rail's `paymentRef` were ever reused (bug, replay, vendor ID rotation), `findFirstRow` returns an arbitrary one of the matches with no tie-break. This is B5.

2. **The idempotency check itself** (`refund_manager.dart:119-125`) — `payment.status == OrderStatus.refunded`, read with no lock, no transaction. `RefundManager` is invoked from webhook handlers that are documented to retry (see A2's wiring order, and the existing Apple/Google `processCallback` paths that already call it today). Two concurrent deliveries for the same refund both read "not yet refunded," both fall through to `_handler`/`_executeAction`, both revoke entitlements. This is B4.

B5 isn't just a performance note — **B4's fix depends on it.** Locking or claiming "the payment this refund is for" only means something if that lookup reliably names one row. Fix the index first.

## B5: `(paymentRail, paymentRef)`, not `paymentRef` alone

`paymentRef` is never generated by this codebase — it's whatever ID string the payment provider issues, written verbatim at delivery time:

| Rail | Write site | Source |
|---|---|---|
| Apple | `apple_iap_rail.dart:321`, `:407` | `transactionId` — Apple's own transaction ID |
| Google | `google_iap_rail.dart:342` | `purchase.orderId ?? ''` |
| Polar | `polar_rail.dart:216` | `validation.id` — Polar's license-key UUID |

Three separate, uncoordinated ID namespaces from three unrelated vendors, each with a different format. Nothing about the *system* guarantees they're disjoint — only the practical fact that Apple's format, Google's `GPA.`-prefixed format, and Polar's UUID format are unlikely to coincide by chance. A global unique constraint on `paymentRef` alone would treat that coincidence as a real conflict; the thing actually worth preventing is one rail reusing (or, under a race, double-writing) the same ref, which is what the constraint should be scoped to.

**Change to `models/transaction_payment.spy.yaml`:**

```yaml
indexes:
  internal_tx_id_idx:
    fields: internalTransactionId
    unique: true
  timestamp_idx:
    fields: transactionTimestamp
    unique: false
  payment_ref_idx:
    fields: paymentRail, paymentRef
    unique: true
```

Per D3, this is a schema change — batch it with any other pending schema work rather than running `serverpod create-migration` for this alone, and remember the cross-module UUID regeneration gotcha in the parent `CLAUDE.md` if this migration touches anything from `anonaccount_server`.

**Aside, not in scope here:** `ReceiptHash.hash` (`models/receipt_hash.spy.yaml`) has the same shape of global-unique-across-rails index, unscoped by `paymentRail`. It's lower risk — `hash` is a SHA-256 digest, not a vendor-formatted ID, so accidental cross-rail collision is negligible even before considering the birthday bound — but it's the same category of decision this spec just made differently for `paymentRef`. Flagging for consistency, not proposing a change; the risk profile is different enough (opaque 256-bit digest vs. vendor ID string) that "leave it" is defensible, but it's the repo owner's call if it comes up again.

**`paymentRef` is also nullable (`String?`) in the current model.** Every actual write site provides a non-null value (Google explicitly falls back to `''`). Tightening it to non-nullable is a reasonable follow-on but is a separate, smaller decision — Postgres unique indexes already treat `NULL` as distinct from every other `NULL`, so a nullable column doesn't break the constraint above; it just means "no ref" rows wouldn't collide with each other either way. Not blocking this spec.

## B4: an idempotency claim, not a bigger lock

The obvious fix — wrap `_resolveContext`'s status check and `_executeAction`'s `_markRefunded` write in one transaction with `LockMode.forUpdate` on the `TransactionPayment` row, mirroring the pattern already used in `entitlement_manager.dart:104-113` and `group_entitlement_manager.dart` — doesn't actually work here, for a reason specific to this method's shape:

**The developer hook decides the outcome, and it runs *between* the read and the write.** `RefundAction.ignore` (`refund_manager.dart:227-228`) deliberately returns without calling `_markRefunded` at all — the hook can choose not to persist a refunded state. That's existing, intentional behavior (`RefundContext`/`RefundHandler` exist specifically so a parent app can override the default `revokeAll`). A single `FOR UPDATE` transaction spanning resolve → hook → execute would hold a row lock across arbitrary developer code for however long the hook takes to run — and `EntitlementManager.revokeEntitlement` / `GroupEntitlementManager.revokeGroupEntitlement` (called inside `_executeAction`) each open their *own* `session.db.transaction(...)` (`entitlement_manager.dart:174`, `group_entitlement_manager.dart:187`) — neither accepts an external transaction to participate in. Making them accept one would be a real API change to methods used well beyond refunds; out of proportion for this fix.

So idempotency and "what should happen" need to be decided by two different mechanisms:

- **Idempotency: has this refund event been claimed already?** — must be atomic, must happen before the hook runs, must not depend on what the hook decides.
- **Outcome: what does `_executeAction` do?** — stays exactly as it is today, hook-driven, unlocked internal transactions per manager call (each already race-safe on its own balance row, per the existing `FOR UPDATE` pattern).

**Design: a dedicated claim row**, unique on the same `(paymentRail, paymentRef)` pair B5 just constrained — same identity, same reasoning about what "this refund" means, kept consistent rather than inventing a second key shape:

```yaml
# models/refund_claim.spy.yaml
class: RefundClaim
table: refund_claim
fields:
  paymentRail: PaymentRail
  paymentRef: String
  claimedAt: DateTime, default=now
indexes:
  refund_claim_idx:
    fields: paymentRail, paymentRef
    unique: true
```

`processRefund` attempts the claim **before** resolving context or calling the hook:

```dart
static Future<void> processRefund(Session session, RefundEvent event) async {
  try {
    await RefundClaim.db.insertRow(
      session,
      RefundClaim(paymentRail: event.rail, paymentRef: event.paymentRef),
    );
  } on DatabaseException {
    // Unique violation: another delivery of the same refund already
    // claimed it. Nothing to do — whatever that delivery decided has
    // already happened or is happening.
    session.log(
      'Refund already claimed: ${event.rail.name}:${event.paymentRef}',
      level: LogLevel.info,
    );
    return;
  }

  final context = await _resolveContext(session, event);
  final action = _handler != null
      ? await _handler!(session, event, context)
      : RefundAction.revokeAll;
  await _executeAction(session, event, context, action);
}
```

Two things to get right that the existing `ReceiptHash` precedent (cited in the original audit as "the better answer") does **not** currently get right, and this fix shouldn't copy blindly:

1. **The exception type.** Confirm what Serverpod actually throws on a unique-constraint violation from `insertRow` before implementing — `on DatabaseException` above is this spec's best guess from the surrounding codebase's exception vocabulary, not a confirmed type. Get it wrong and a genuine duplicate-delivery race throws an unhandled error instead of a clean no-op, which is worse than today's bug (today's bug silently double-revokes; a wrong catch clause would 500 on every retried webhook).
2. **Catch it at the insert, not with a pre-check.** The delivery-side precedent this echoes (`polar_rail.dart:94-96`, and Apple/Google's equivalents) checks `findFirstRow` *before* inserting and has no `try`/`catch` around the insert itself — meaning it only fixes sequential re-delivery, not genuinely concurrent delivery (two inserts racing each other would have both passed the pre-check). Don't repeat that gap here: the pre-check is unnecessary — the insert's unique constraint is the actual safety mechanism, atomic at the Postgres level regardless of app-level timing, and the `catch` is what makes the failure path graceful instead of a crash.

**Why not reuse `OrderStatus.processing`?** `TransactionPayment`'s existing `OrderStatus` enum (`models/order_status.spy.yaml`) already has a `processing` value — tempting to avoid a new table by writing that as a claim marker. Rejected: it's unused today (no write site sets it — only referenced in generated deserialization code) and its name means "the purchase is being processed," a pre-paid state. Repurposing it for "a refund claim is in flight" — a post-paid, different-direction concept — would be the kind of silent semantic drift this repo's own comment discipline exists to prevent. A new, narrowly-named table costs one small migration and says exactly what it does.

## Non-goals

- **Not fixing `CommerceManager.fulfillTransactionPayment`'s idempotency gap** (CRITICAL/HIGH #5 in the original audit, `commerce_manager.dart:140-165`). Different shape, and actually simpler: that method already wraps everything in one `session.db.transaction(...)` and does the status check/write inside it — it's just missing `lockMode: LockMode.forUpdate` on the one `findFirstRow`. A near one-line fix once someone picks it up; not bundled here because it's a different call site with a different (simpler) root cause, and the user's ordering for this pass was B4+B5 specifically.
- **Not touching `EntitlementManager`/`GroupEntitlementManager`.** Their existing per-row `FOR UPDATE` locks are correct and sufficient for what they do; this spec works around their transaction boundaries rather than changing them.
- **Not deduping** — same reasoning as A2: this is a correctness fix landing in code the eventual rails dedupe would otherwise template from.
